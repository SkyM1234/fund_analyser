# 评价指标说明文档

本文档详细说明基金分析系统评测框架中的所有评价指标，包括含义、计算方法和适用场景。

---

## 一、检索类指标 (Retrieval Metrics)

这些指标用于评估信息检索（IR）模块的性能，衡量检索结果的质量和相关性。

### 1.1 Hit Rate（命中率）

**含义**：在返回的 Top-K 结果中，至少包含一个相关文档的比例。这是一个二元指标。

**计算方法**：
```
Hit Rate = 1  (如果结果中至少有一个相关文档)
         = 0  (如果结果中没有任何相关文档)
```

**取值范围**：`{0.0, 1.0}`

**判断逻辑**：
- 优先使用 `relevant_chunk_ids` 进行精确匹配
- 其次使用 `expected_fund_codes` 匹配基金代码
- 最后使用 `relevant_keywords` 进行关键词子串匹配

**适用场景**：适合快速判断检索系统是否能够找到至少一个相关结果，是最基础的检索评估指标。

---

### 1.2 MRR（Mean Reciprocal Rank，平均倒数排名）

**含义**：首个相关结果在排名中位置的倒数，衡量第一个相关结果出现的位置有多靠前。

**计算方法**：
```
MRR = 1 / rank  (rank 是第一个相关结果的排名位置，从1开始)
    = 0         (如果没有相关结果)
```

**示例**：
- 第1个结果相关：MRR = 1.0
- 第2个结果相关：MRR = 0.5
- 第5个结果相关：MRR = 0.2
- 无相关结果：MRR = 0.0

**取值范围**：`[0.0, 1.0]`

**适用场景**：关注第一个相关结果的排名位置，适合用户只看前几个结果的场景（如搜索引擎）。

---

### 1.3 NDCG（Normalized Discounted Cumulative Gain，归一化折损累积增益）

**含义**：考虑所有结果的相关性和位置的综合排序质量指标，位置越靠前权重越大。

**计算方法**：

1. **DCG（Discounted Cumulative Gain）**：
```
DCG = Σ (rel_i / log₂(i + 2))
```
其中 `rel_i` 是第 i 个结果的相关性分数（0或1），i 从0开始。

2. **IDCG（Ideal DCG）**：
假设所有相关结果都排在最前面时的理想 DCG 值。

3. **NDCG**：
```
NDCG = DCG / IDCG
```

**示例**：
假设返回5个结果，相关性为 `[1, 0, 1, 0, 0]`（1表示相关，0表示不相关）
- DCG = 1/log₂(2) + 0/log₂(3) + 1/log₂(4) + ... = 1.0 + 0 + 0.5 + 0 + 0 = 1.5
- 理想情况下相关性为 `[1, 1, 0, 0, 0]`
- IDCG = 1/log₂(2) + 1/log₂(3) = 1.0 + 0.631 = 1.631
- NDCG = 1.5 / 1.631 ≈ 0.92

**取值范围**：`[0.0, 1.0]`

**适用场景**：综合评估整个结果列表的排序质量，是信息检索中最常用的标准指标之一。

---

### 1.4 Fund Code Recall（基金代码召回率）

**含义**：期望的基金代码在检索结果中出现的比例，专门用于评估基金代码过滤功能。

**计算方法**：
```
Fund Code Recall = |expected_codes ∩ retrieved_codes| / |expected_codes|
```

**示例**：
- 期望基金：`['000001', '000002', '000003']`
- 检索到的基金：`['000001', '000003', '000004']`
- Recall = 2 / 3 ≈ 0.67

**取值范围**：`[0.0, 1.0]`

**特殊情况**：如果没有期望基金代码（`expected_fund_codes` 为空），返回 1.0 并标注"no expected codes"。

**适用场景**：针对 `filter_fund_code` 场景，能直接检测基金代码过滤是否失效。

## 二、回答类指标 (Answer Metrics)

这些指标用于评估生成回答的质量，包括引用准确性、拒答行为和事实覆盖度。

### 2.1 Citation Accuracy（引用准确率）

**含义**：回答中引用的基金代码与期望引用基金代码的匹配程度，使用 F1 分数综合考虑精确率和召回率。

**计算方法**：

1. **Precision（精确率）**：
```
Precision = |cited ∩ expected| / |cited|
```

2. **Recall（召回率）**：
```
Recall = |cited ∩ expected| / |expected|
```

3. **F1 Score**：
```
F1 = 2 × (Precision × Recall) / (Precision + Recall)
   = 0  (当 Precision + Recall = 0 时)
```

**示例**：
- 期望引用：`['000001', '000002', '000003']`
- 实际引用：`['000001', '000002', '000004']`
- Overlap = `['000001', '000002']`
- Precision = 2/3 ≈ 0.67
- Recall = 2/3 ≈ 0.67
- F1 = 2 × 0.67 × 0.67 / (0.67 + 0.67) ≈ 0.67

**取值范围**：`[0.0, 1.0]`

**特殊情况**：
- 如果没有期望引用（闲聊、敏感问题等），返回 1.0 并标注"no expected codes"
- 如果没有实际引用但有期望引用，返回 0.0

**适用场景**：评估回答是否引用了正确的基金，避免引用错误或无关基金。

---

### 2.2 Refusal Correctness（拒绝准确率）

**含义**：系统对敏感问题的拒答行为是否正确。敏感问题应该拒答，非敏感问题不应拒答。

**计算方法**：
```
Refusal Correctness = 1  (如果 is_refused == should_refuse)
                    = 0  (如果 is_refused != should_refuse)
```

其中：
- `should_refuse`：标注数据中标明是否应该拒答
- `is_refused`：检测回答中是否包含拒答标记词

**拒答标记词**：
- "不能提供具体的投资建议"
- "不提供投资建议"
- "无法给出具体推荐"
- "请咨询专业的投资顾问"
- "投资有风险"

**取值范围**：`{0.0, 1.0}`

**错误类型**：
- **False Positive**：不应拒答但拒答了（过度保守）
- **False Negative**：应该拒答但没拒答（合规风险）

**适用场景**：确保系统符合金融合规要求，对投资建议等敏感问题进行合理拒答。

---

### 2.3 Key Fact Coverage（关键事实覆盖率）

**含义**：标注的关键事实在回答中出现的比例，用于衡量回答是否涵盖了核心信息。

**计算方法**：
```
Key Fact Coverage = (命中的关键事实数量) / (总关键事实数量)
```

匹配方式为简单子串匹配：如果关键事实作为子串出现在回答中，则视为命中。

**示例**：
- 关键事实：`['年化收益率10%', '风险等级为中高', '基金经理张三']`
- 回答包含："该基金年化收益率10%，由基金经理张三管理"
- 命中数：2（缺少风险等级信息）
- Coverage = 2/3 ≈ 0.67

**取值范围**：`[0.0, 1.0]`

**特殊情况**：如果没有关键事实标注，返回 1.0 并标注"no key_facts"。

**优缺点**：
- **优点**：粗粒度但确定性强，计算简单快速
- **缺点**：只能检测完全匹配的字符串，无法识别语义等价表达
- **互补性**：可与 LLM-judge 的 correctness 指标互补使用

**适用场景**：快速检查回答是否包含必须提及的关键信息点。

---

### 2.4 Intent Accuracy（意图准确率）

**含义**：路由识别的意图是否与标注的期望意图一致，用于评估意图分类器的准确性。

**计算方法**：
```
Intent Accuracy = 1  (如果 actual_intent == expected_intent)
                = 0  (如果 actual_intent != expected_intent)
```

**取值范围**：`{0.0, 1.0}`

**特殊情况**：如果没有期望意图标注，返回 1.0 并标注"no expected intent"。

**适用场景**：评估路由模块对用户查询意图的分类能力，是可选指标。

## 三、LLM-as-Judge 指标

这些指标使用大语言模型作为评判者，评估更复杂的语义层面质量。所有指标返回 0.0~1.0 的浮点分数。

### 配置特点：
- **temperature=0**：确保确定性输出
- **严格 JSON 输出**：避免解析失败
- **独立模型**：judge 模型可单独配置，不与业务 LLM 绑定

---

### 3.1 Context Relevance（检索上下文相关性）

**含义**：检索结果整体上对用户问题的语义相关程度。

**评判依据**：
- 输入：用户问题 + 检索结果列表
- 无需 ground truth

**打分标准**：
- **1.0**：检索结果中多数片段与问题高度相关
- **0.5**：部分相关，多数无关或冗余
- **0.0**：几乎无相关内容

**计算方法**：
1. 将检索结果格式化为上下文字符串（最多4000字符）
2. 构造提示词：包含用户问题和检索上下文
3. 调用 judge LLM 输出 JSON：`{"score": 0.8, "reason": "..."}`
4. 解析 JSON 获取分数

**取值范围**：`[0.0, 1.0]`（LLM 可输出中间值）

**适用场景**：评估检索质量，无需人工标注相关文档，成本较低。

---

### 3.2 Correctness（回答正确性）

**含义**：模型回答与参考答案在事实和结论上的语义一致性。

**评判依据**：
- 输入：用户问题 + 参考答案 + 模型回答
- 需要 ground truth（参考答案）

**打分标准**：
- **1.0**：关键事实/结论完全一致
- **0.7**：主要点一致，存在小遗漏
- **0.3**：部分一致或方向偏差
- **0.0**：错误或不相关

**计算方法**：
1. 从 ground truth 中获取参考答案
2. 构造提示词：包含问题、参考答案、模型回答
3. 调用 judge LLM 输出 JSON
4. 解析获取分数

**取值范围**：`[0.0, 1.0]`

**特殊情况**：如果没有参考答案，返回 1.0 并标注"no reference"。

**适用场景**：评估回答的准确性，是最核心的 LLM-judge 指标。

---

### 3.3 Faithfulness（事实忠实度）

**含义**：模型回答中的陈述是否**仅基于**检索上下文，不包含上下文之外的虚构内容。用于检测幻觉（hallucination）。

**评判依据**：
- 输入：用户问题 + 检索上下文 + 模型回答
- 需要检索结果（retrieved_chunks）

**打分标准**：
- **1.0**：所有断言都能在上下文中找到支撑
- **0.7**：主要断言有支撑，少量泛化或常识补充
- **0.3**：存在明显未支撑的具体数字/事实
- **0.0**：大量编造或与上下文矛盾

**特殊规则**：
- 如果回答只是合规拒答（不输出基金事实），视为 1.0
- 如果没有检索上下文，返回 1.0 并标注"no retrieved context"

**计算方法**：
1. 从 outputs 中获取检索片段（retrieved_chunks）
2. 格式化为上下文字符串
3. 构造提示词：强调检查是否有未支撑的陈述
4. 调用 judge LLM 输出 JSON
5. 解析获取分数

**取值范围**：`[0.0, 1.0]`

**适用场景**：抓取 RAG 系统中的幻觉问题，确保回答有据可依。

---

### 3.4 Answer Relevance（回答相关性）

**含义**：模型回答是否切题回应了用户问题，不评价正确性，只看是否答非所问。

**评判依据**：
- 输入：用户问题 + 模型回答
- 无需 ground truth 或检索上下文

**打分标准**：
- **1.0**：直接回应问题
- **0.5**：部分相关或答非所重点
- **0.0**：答非所问

**计算方法**：
1. 构造提示词：包含问题和回答
2. 调用 judge LLM 输出 JSON
3. 解析获取分数

**取值范围**：`[0.0, 1.0]`

**与 Correctness 的区别**：
- Correctness：评估回答是否正确（需要参考答案）
- Relevance：评估回答是否切题（不需要参考答案）

**适用场景**：检测模型是否理解问题并给出相关回答，成本较低。

## 四、指标总结与选择建议

### 4.1 指标分类

| 类别 | 指标 | 是否需要标注 | 计算成本 | 主要用途 |
|------|------|------------|---------|---------|
| **检索类** | Hit Rate | 需要 | 低 | 基础检索能力 |
| | MRR | 需要 | 低 | 首个相关结果位置 |
| | NDCG | 需要 | 低 | 综合排序质量 |
| | Fund Code Recall | 需要 | 低 | 基金代码过滤 |
| **回答类（规则）** | Citation Accuracy | 需要 | 低 | 引用基金准确性 |
| | Refusal Correctness | 需要 | 低 | 拒答行为正确性 |
| | Key Fact Coverage | 需要 | 低 | 关键信息覆盖 |
| | Intent Accuracy | 需要 | 低 | 意图识别准确性 |
| **LLM-Judge** | Context Relevance | 不需要 | 高 | 检索质量评估 |
| | Correctness | 需要 | 高 | 回答准确性 |
| | Faithfulness | 不需要 | 高 | 幻觉检测 |
| | Answer Relevance | 不需要 | 高 | 回答切题性 |

### 4.2 指标组合建议

**最小评测集**（快速迭代）：
- Hit Rate（检索）
- Citation Accuracy（引用）
- Refusal Correctness（合规）

**标准评测集**（日常评测）：
- NDCG（检索质量）
- Fund Code Recall（代码过滤）
- Citation Accuracy（引用准确）
- Key Fact Coverage（事实覆盖）
- Refusal Correctness（拒答正确）

**完整评测集**（深度评测）：
- 所有规则指标
- Context Relevance（检索相关性）
- Correctness（回答正确性）
- Faithfulness（事实忠实度）
- Answer Relevance（回答相关性）

### 4.3 使用注意事项

1. **标注成本**：规则指标需要详细标注（期望基金、关键事实等），LLM-judge 部分指标可降低标注成本
2. **计算成本**：LLM-judge 指标需要调用 LLM，成本较高，适合小规模深度评测
3. **互补性**：规则指标确定性强但覆盖有限；LLM-judge 灵活但有随机性，建议组合使用
4. **业务特点**：
   - 金融合规场景：重点关注 Refusal Correctness
   - 基金代码过滤：重点关注 Fund Code Recall
   - RAG 幻觉问题：重点关注 Faithfulness
   - 回答质量：重点关注 Correctness 和 Key Fact Coverage
